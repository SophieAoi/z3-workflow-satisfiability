## The problem

Given a set of users $U$ and workflow steps $S$, find a plan $\pi : S \to U$ that satisfies all the constraints. Every step gets exactly one user; a user can do any number of steps, including none.

The solver outputs `sat` with a plan or `unsat`. For sat instances it also has to say whether the plan is the only solution.

### Constraint types (Appendix 1)

| Constraint | File syntax | Requirement |
|---|---|---|
| Authorisations $(u, A)$ | `Authorisations u1 s1 s2` | $\pi(s) = u \Rightarrow s \in A$. Users without an Authorisations line can do any step. `Authorisations u1` with no steps means u1 can do nothing. |
| Separation of duty $(s', s'')$ | `Separation-of-duty s1 s2` | $\pi(s') \neq \pi(s'')$ |
| Binding of duty $(s', s'')$ | `Binding-of-duty s1 s3` | $\pi(s') = \pi(s'')$ |
| At-most-k $(k, T)$ | `At-most-k 2 s1 s2 s3` | $\lvert\{\pi(s) : s \in T\}\rvert \le k$ |
| One-team $(T, U_1..U_r)$ | `One-team s1 s2 s4 (u1 u2) (u5 u7 u8) (u3)` | $\{\pi(s) : s \in T\} \subseteq U_i$ for some $i$ (teams are disjoint) |
| Binding of order $(s', s'')$ | `Binding-of-order s1 s3` | $\pi(s') \le \pi(s'')$ in the user order $u_1 < u_2 < \dots$ (our sixth type, not in the appendix) |

### Input format

```
#Steps: 3
#Users: 4
#Constraints: 6
Authorisations u1 s1 s2
...
```

Keywords are case-insensitive, extra whitespace is allowed, and steps and users are numbered from 1. The provided files have CRLF line endings.

### Output format

Same as the module template and `transform_output` helper:

```
sat
s1: u3
s2: u1
s3: u3
this is the only solution      # or: other solutions exist
12ms
```

## Formulations

### One-hot encoding (`cp-sat`, `z3-bool`)

$x_{s,u}$ is true iff $\pi(s) = u$. It is only created when $u$ is authorised for $s$, which covers the Authorisations constraint. This is written once in `BooleanEncoding`; `CpSatBooleanModel` and `Z3BooleanModel` just supply the solver calls.

| Constraint | Encoding |
|---|---|
| One user per step | $\text{ExactlyOne}_u\, x_{s,u}$ |
| SoD $(a,b)$ | $\neg x_{a,u} \lor \neg x_{b,u}$ for each $u$ |
| BoD $(a,b)$ | $x_{a,u} \leftrightarrow x_{b,u}$ for each $u$; users eligible for only one of the steps are set false |
| Bo2 $(a,b)$ | per-step chain $o_{s,u} := (\pi(s) \ge u)$, defined by $o_{s,u} \leftrightarrow (o_{s,u-1} \land \neg x_{s,u-1})$; the rule is $o_{a,u} \rightarrow o_{b,u}$ for each $u \ge 1$. Linear in $|U|$, and the chain is built only for steps that appear in a Bo2 constraint. |
| At-most-k | $m_{s,t}$ means "s and t have the same user" ($m_{s,t} \land x_{s,u} \rightarrow x_{t,u}$). $f_i \lor \bigvee_{j<i} m_{t_j,t_i}$ marks a step with a new user; $\text{AtMost}_k(f)$. Plus transitivity clauses on $m$. |
| One-team | team selectors $z_i$ with $\text{ExactlyOne}_i\, z_i$ and $x_{s,u} \rightarrow z_{team(u)}$; users in no team are set false |
| Uniqueness | add $\bigvee_s \neg x_{s,\pi^*(s)}$ and solve again |

z3 uses `PbEq` and `AtMost` with the `QF_FD` solver. Only the $x$ variables are blocked for uniqueness, since blocking the auxiliary ones could exclude the same plan or miss a different one.

### Integer encoding (`z3-int`)

One integer $\pi_s \in [0, n)$ per step:

| Constraint | Encoding |
|---|---|
| Authorisation | $\bigvee_{u \text{ authorised for } s} \pi_s = u$ |
| SoD / BoD | $\pi_a \ne \pi_b$ / $\pi_a = \pi_b$ |
| Bo2 $(a,b)$ | $\pi_a \le \pi_b$ (one native inequality) |
| At-most-k | $\sum_i [\bigwedge_{j<i} \pi_{t_j} \ne \pi_{t_i}] \le k$ |
| One-team | $\bigvee_i \bigwedge_{s \in T} \bigvee_{u \in U_i} \pi_s = u$ |
| Uniqueness | add $\bigvee_s \pi_s \ne \pi^*(s)$ and solve again |

### Alternative: per-user at-most-k (`cp-sat-users`)

Same as `cp-sat` except for at-most-k, which counts users directly instead of going through step pairs:

$$y_u \text{ for each user eligible for a step in } T,\qquad x_{s,u} \rightarrow y_u \ (s \in T),\qquad \text{AtMost}_k(y)$$

It is the most literal reading of $\lvert\{\pi(s) : s \in T\}\rvert \le k$. $y_u$ can be true for an unused user, which only over-counts, so it is sound, and the solver can always set $y_u$ to the truth, so it is complete. With hundreds of eligible users the cardinality constraint is over a big set and propagates badly, which is why the pairwise version is the default. This was our first phase 1 version; it is now a selectable method so the two can be compared directly (`CpSatUserAmkModel`, set via `AMK_ENCODING = "users"`).

### Alternative: pure clausal form (`z3-cnf`)

Same variables and clauses as `z3-bool`, but with no cardinality atoms at all, so every constraint the solver sees is a clause:

| Primitive | Clauses |
|---|---|
| $a \leftrightarrow b$ | $(\neg a \lor b) \land (a \lor \neg b)$ |
| $\text{AtMost}_k(x_1..x_n)$ | sequential counter (Sinz, 2005): auxiliary $r_{i,j}$ = "at least $j+1$ of $x_1..x_{i+1}$ are true"; $O(nk)$ clauses and variables |
| $\text{ExactlyOne}(x_1..x_n)$ | $(x_1 \lor \dots \lor x_n) \land \text{AtMost}_1(x_1..x_n)$ |

So the whole problem is in conjunctive normal form, solved by z3's SAT core (`QF_FD`). Comparing it with `z3-bool` shows what native cardinality reasoning gains over encoding the counting in clauses. `test_formulations.py` checks the counter exhaustively for $n \le 6$ and every $k$, and checks that the z3 model really contains only clauses.

### Notes

- **At-most-k encoding** (`cp-sat` vs `cp-sat-users`, everything else identical): the per-user version times out on all of `4-constraint-hard` and example19, and takes 16–37 s on examples 16–18, where the pairwise version takes 0.6–2 s. On small and medium instances the two are the same. With hundreds of eligible users, $	ext{AtMost}_k(y)$ ranges over a big set and propagates badly; the pairwise version only counts over the $|T|$ steps.
- **Integer vs one-hot in z3** (`z3-int` vs `z3-bool`): `z3-int` keeps up with `cp-sat` on small and medium instances (and is the fastest on `4-constraint`), but times out on examples 17 and 19 and all of `4-constraint-hard`. We also tried other z3 logics (`QF_FD`, `QF_LIA`), users as an enum sort or bit-vectors, and an implied constraint for at-most-k; none of them fixed it. Our guess is that each $\pi_a 
e \pi_b$ becomes a case split ($<$ or $>$) in integer arithmetic. With the one-hot encoding the same z3 solves everything, which fits that explanation. The one exception is example16 (`z3-int` 9 s vs `z3-bool` 14 s), possibly because it is the only large example with unrestricted users (90 of 500), which add many one-hot variables. Not checked.
- **Native cardinality vs clauses** (`z3-bool` vs `z3-cnf`): almost the same on the hard family (3.5 s median for both) and on the large examples. On the medium families `z3-cnf` is 1.3–2.4x slower, presumably the cost of the extra sequential-counter variables. So z3's native cardinality handling helps less than we expected here; most of the work is the clause part of the encoding, which is shared.
- **Solver** (`cp-sat` vs `z3-bool`, same encoding): CP-SAT is faster on everything except the tiny instances, where its fixed start-up cost (~2–3 ms) dominates. Probably because it runs a parallel portfolio of search strategies (4 workers here) and z3 runs one.
- **Portfolio** gives `cp-sat`'s times, since `cp-sat` settles every instance first. The fallback only matters when `cp-sat` hits a time limit (tested in `tests/test_pruning_and_portfolio.py`).
- **`QF_FD`** was faster than z3's default solver on every large instance we tried for `z3-bool` (e.g. 22 s vs 88 s on example16, 3.5 s vs 37 s on `4-constraint-hard/2`), so it is the default (`logic=None` switches back).
- Times vary by up to about 2x between runs on the same machine.
